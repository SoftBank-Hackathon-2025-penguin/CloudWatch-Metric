## 🎯 1. 메트릭 가중치: 50% / 35% / 15%

```python
METRIC_WEIGHTS = {
    'error_rate': 0.50,  # 50%
    'latency': 0.35,     # 35%
    'cpu': 0.15          # 15%
}
```

### 왜 이렇게 정했나요?

#### 에러율이 50%인 이유:
```
사용자 입장에서 가장 치명적인 건?
→ 에러 발생 (5XX 에러)

에러가 나면:
❌ 기능 자체가 안 됨
❌ 사용자가 서비스를 못 씀
❌ 매출 손실 직결
❌ 신뢰도 하락

→ 따라서 "가장 중요"
→ 50% 가중치
```

**실제 사례:**
- Netflix: "1% 에러율 = 수백만 달러 손실"
- Amazon: "100ms 느린 것보다 에러 1개가 더 치명적"

---

#### 레이턴시가 35%인 이유:
```
응답 속도가 느리면?
→ 사용자 짜증 나지만, 일단 "작동은 함"

느린 건 참을 수 있지만:
⚠️ 너무 느리면 이탈
⚠️ UX 나빠짐
⚠️ 매출 감소

→ "중요하지만, 에러보단 덜 치명적"
→ 35% 가중치
```

**실제 데이터:**
- Google 연구: "0.5초 늦으면 트래픽 20% 감소"
- 하지만 에러보다는 덜 심각

---

#### CPU가 15%인 이유:
```
CPU 높으면?
→ 사용자는 모름 (백엔드 문제)

CPU 80%여도:
✅ 서비스는 정상 작동
✅ 에러도 안 남
⚠️ 단, 스케일링 필요

→ "모니터링은 필요하지만, 당장 치명적이진 않음"
→ 15% 가중치
```

**비유:**
```
에러율: 심장마비 (즉시 치명적) → 50%
레이턴시: 다리 저림 (불편함) → 35%
CPU: 체온 상승 (주의 필요) → 15%
```

---

### 다른 비율은 안 되나요?

시도해본 다른 비율들:

#### ❌ 균등 분배 (33% / 33% / 33%)
```
문제: 에러와 CPU를 동등하게 취급
→ CPU 80%인데 에러 없으면: 점수 33점 (너무 높음)
→ 에러 5%인데 CPU 정상이면: 점수 16점 (너무 낮음)

결론: 현실과 안 맞음
```

#### ❌ 에러 중심 (70% / 20% / 10%)
```
문제: 레이턴시 무시
→ 에러 없는데 응답 5초: 점수 20점 (너무 낮음)
→ 사용자는 짜증나는데 점수는 좋음

결론: 레이턴시도 중요함을 간과
```

#### ✅ 현재 (50% / 35% / 15%)
```
장점:
✅ 에러를 가장 중요하게 취급
✅ 레이턴시도 충분히 반영
✅ CPU는 조기 경고 역할
✅ 실제 비즈니스 임팩트 반영

결론: 균형 잡힘!
```

## 📊 2. 점수 구간: 0-30 / 31-70 / 71-100

```python
STATE_SCORE_RANGES = {
    'healthy': (0, 30),    # 0~30점
    'warning': (31, 70),   # 31~70점
    'danger': (71, 100)    # 71~100점
}
```

### 왜 이렇게 나눴나요?

#### 3단계 vs 5단계?

**❌ 2단계 (정상/위험)**
```
문제: 너무 단순
→ 조기 경고 불가
→ "정상" → 갑자기 "위험" (충격적)

예시:
점수 49: 정상
점수 51: 위험 ← 너무 급격함
```

**❌ 5단계 (완벽/좋음/보통/주의/위험)**
```
문제: 너무 복잡
→ 사용자 혼란
→ "보통"과 "주의"의 차이가 뭐지?
→ 구현 복잡도 증가

해커톤 3일 안에 완성 불가능
```

**✅ 3단계 (건강/주의/위험)**
```
장점:
✅ 신호등과 동일 (🟢🟡🔴)
✅ 직관적
✅ 조기 경고 가능
✅ 구현 간단

→ 사용자가 이미 익숙함!
```

---

#### 왜 0-30 / 31-70 / 71-100인가요?

**"0-30"이 Healthy인 이유:**
```
0~30점 = 상위 30%
→ 대부분의 서비스는 30점 이하
→ 너무 엄격하면 항상 "주의" 상태
→ 사용자 피로도 증가

실제 데이터:
- AWS Best Practice: 에러율 1% 이하
- Google SRE: 99.9% 가용성
→ 정상 서비스는 대부분 0~20점
```

**"31-70"이 Warning인 이유:**
```
중간 구간 = 40점 폭
→ 조기 경고용
→ "아직 괜찮지만, 지켜봐야 함"

31점: 약간 높아졌네?
50점: 좀 신경 써야겠는데?
70점: 위험 직전!

→ 충분한 경고 시간 제공
```

**"71-100"이 Danger인 이유:**
```
71점 이상 = 즉시 조치 필요
→ 에러율 5% 이상
→ 또는 레이턴시 1500ms 이상

실무에서:
- 에러율 5% = PagerDuty 알림
- 레이턴시 1.5초 = 사용자 이탈 시작

→ 실제로 위험한 수준
```

## 🎚️ 3. Fallback 임계값

```python
FALLBACK_THRESHOLDS = {
    'error_rate': ThresholdConfig(
        normal=1.0,    # 1% 이하
        warning=5.0,   # 5% 이하
        danger=10.0    # 10% 이상
    ),
    'latency': ThresholdConfig(
        normal=300,    # 300ms 이하
        warning=700,   # 700ms 이하
        danger=1500    # 1500ms 이상
    ),
    'cpu': ThresholdConfig(
        normal=50,     # 50% 이하
        warning=80,    # 80% 이하
        danger=95      # 95% 이상
    )
}
```

---

### 에러율: 1% / 5% / 10%

#### 1% (Normal) 이유:
```
업계 표준: "99% 가용성"
→ 에러율 1% = 99% 성공
→ 대부분의 서비스 목표치

실제:
- AWS SLA: 99.99% (0.01% 에러)
- Google: 99.9% (0.1% 에러)
- 일반 스타트업: 99% (1% 에러)

→ 1%는 "허용 가능한 상한선"
```

#### 5% (Warning) 이유:
```
5% 에러 = 20명 중 1명 에러
→ 사용자가 체감하기 시작
→ 조사 필요

실무:
- 5% 넘으면 알림 받음
- 10분 이내 원인 파악
```

#### 10% (Danger) 이유:
```
10% 에러 = 10명 중 1명 에러
→ 심각한 장애
→ 즉시 롤백 고려

실제 사례:
- Facebook 장애: 에러율 15% → 1시간 내 롤백
- Twitter 장애: 에러율 12% → 긴급 패치
```

---

### 레이턴시: 300ms / 700ms / 1500ms

#### 300ms (Normal) 이유:
```
사용자 체감 기준:
- 100ms 이하: 즉각 반응 (불가능)
- 300ms 이하: 빠르다고 느낌 ✅
- 1000ms 이상: 느리다고 느낌

Google 연구:
- 300ms = 사용자 만족
- 500ms = 약간 느림
```

#### 700ms (Warning) 이유:
```
700ms = 0.7초
→ 사용자가 "어? 느리네?" 느끼기 시작
→ 아직 참을 수 있지만 짜증

실무:
- 500~1000ms: 모니터링 구간
- 700ms = 중간값
```

#### 1500ms (Danger) 이유:
```
1.5초 = 사용자 이탈 시작
→ "이 사이트 느려" 생각
→ 뒤로가기 클릭 시작

실제 데이터:
- Amazon: 100ms 늦으면 매출 1% 감소
- Google: 500ms 늦으면 트래픽 20% 감소
- 1.5초 = 심각한 수준
```

---

### CPU: 50% / 80% / 95%

#### 50% (Normal) 이유:
```
CPU 50% = 여유로운 상태
→ 트래픽 급증해도 대응 가능
→ 스파이크 흡수 가능

AWS Best Practice:
- 평상시 40~60% 유지
- 오토스케일링 여유 확보
```

#### 80% (Warning) 이유:
```
CPU 80% = 오토스케일링 고려
→ 더 이상 여유 없음
→ 트래픽 조금만 증가해도 위험

실무:
- 80% 넘으면 스케일 아웃
- CloudWatch 기본 임계값도 80%
```

#### 95% (Danger) 이유:
```
CPU 95% = 포화 상태
→ 요청 처리 지연
→ 응답 시간 증가
→ 잠재적 서비스 중단

100% 아닌 이유:
→ 95%부터 이미 지연 발생
→ 100% 되면 이미 늦음
```

## 🧮 4. 심각도 계산 수식

### 선형 vs 지수 vs 계단?

```python
# 우리 방식: 선형 + 구간별
if value <= threshold.normal:
    return 0.0
elif value <= threshold.warning:
    ratio = (value - normal) / (warning - normal)
    return ratio * 0.5  # 0.0 → 0.5
elif value <= threshold.danger:
    ratio = (value - warning) / (danger - warning)
    return 0.5 + (ratio * 0.3)  # 0.5 → 0.8
else:
    ratio = (value - danger) / danger
    return 0.8 + (ratio * 0.2)  # 0.8 → 1.0
```

### 왜 이 방식인가요?

#### ❌ 지수 함수
```python
# 예시: severity = value^2 / threshold^2
# 문제: 너무 급격하게 증가
에러율 1% → 심각도 0.01
에러율 2% → 심각도 0.04
에러율 5% → 심각도 0.25
에러율 10% → 심각도 1.0

→ 작은 변화에 너무 민감
→ 사용자 혼란
```

#### ❌ 계단 함수
```python
# 예시: 구간별 고정값
if value <= 1%: return 0.0
elif value <= 5%: return 0.5
else: return 1.0

→ 1.0%와 4.9%가 같은 점수
→ 너무 단순
```

#### ✅ 구간별 선형
```
장점:
✅ 부드러운 변화
✅ 예측 가능
✅ 직관적

예시 (에러율):
0.5% → 심각도 0.0
1.5% → 심각도 0.125
3.0% → 심각도 0.3
6.0% → 심각도 0.56
10.0% → 심각도 0.8
```

---

### 왜 0.5 / 0.3 / 0.2로 나눴나요?

```
Normal → Warning: 0.0 → 0.5 (50% 증가)
Warning → Danger: 0.5 → 0.8 (30% 증가)
Danger → Critical: 0.8 → 1.0 (20% 증가)
```

**이유:**
```
초반 구간 (Normal → Warning):
→ 큰 변화폭 (0.5)
→ "약간 높아졌네?" 확실히 알림

중간 구간 (Warning → Danger):
→ 중간 변화폭 (0.3)
→ "진짜 위험하네?" 경고

후반 구간 (Danger → Critical):
→ 작은 변화폭 (0.2)
→ 이미 위험, 더 올라도 큰 차이 없음
```

**그래프로 보면:**
```
심각도
1.0 ┤                    ╱─
    │                 ╱
0.8 ┤              ╱
    │           ╱
0.5 ┤      ╱────
    │   ╱
0.0 ┼──────────────────────> 메트릭 값
    0  1%  5%  10%

→ 초반에 가파르게, 후반에 완만하게
```

## 🎯 5. Anomaly Detection 배수: 2.0

```python
deviation = (value - band_upper) / band_upper
severity = min(1.0, deviation * 2.0)
```

### 왜 2.0을 곱하나요?

#### 예시:

```
Anomaly Band: 200ms ~ 600ms
평소: 400ms (정상)

시나리오 1: 900ms
deviation = (900 - 600) / 600 = 0.5 (50% 초과)
severity = 0.5 * 2.0 = 1.0 (최대 위험)

시나리오 2: 750ms
deviation = (750 - 600) / 600 = 0.25 (25% 초과)
severity = 0.25 * 2.0 = 0.5 (주의)

시나리오 3: 650ms
deviation = (650 - 600) / 600 = 0.083 (8% 초과)
severity = 0.083 * 2.0 = 0.17 (약간 높음)
```

**2.0을 선택한 이유:**
```
50% 벗어나면 = 최대 위험 (심각도 1.0)

왜 50%?
→ CloudWatch Anomaly Detection은 보수적
→ 밴드 폭이 꽤 넓음
→ 50% 벗어나면 진짜 이상한 것

다른 배수는?
1.0배: 너무 느슨 (100% 벗어나야 위험)
3.0배: 너무 엄격 (33% 벗어나면 위험)
2.0배: 적당함 ✅
```
