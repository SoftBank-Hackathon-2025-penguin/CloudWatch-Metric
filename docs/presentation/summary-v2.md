## 💭 2025-11-20 오전 - 혼자 브레인스토밍

### 질문 1: "즐거운 배포"를 어떻게 만들까?

#### 검토한 아이디어들

**아이디어 A: 알람만**
```
장점: 간단함
단점: 재미없음, 기존 시스템과 동일
결정: ❌ 탈락
이유: 차별화 없음
```

**아이디어 B: 복잡한 대시보드**
```
장점: 전문적
단점: 초보자 이해 어려움, "즐겁다" 느낌 없음
결정: ❌ 탈락
이유: 해커톤 주제와 맞지 않음
```

**아이디어 C: 점수 + 캐릭터**
```
장점: 직관적, 재미있음, 게임처럼 느껴짐
단점: 캐릭터 에셋 필요
결정: ✅ 선택!
이유:
  - 0~100점 → 누구나 이해
  - 펭귄 → 감정적 연결
  - 게이미피케이션 → "즐거운" 경험
```

### 질문 2: 점수를 어떻게 계산할까?

#### 검토한 방법들

**방법 A: 고정 임계값**
```
에러율 > 5% → 위험
레이턴시 > 1000ms → 위험

장점: 단순, 명확
단점: "평소와 다른가?"를 판단 못함
결정: ❌
이유: Anomaly Detection 활용 못함
```

**방법 B: Anomaly Detection만**
```
ML 밴드 벗어남 → 위험

장점: 지능적, ML 활용
단점: 초기 데이터 없으면 작동 안 함
결정: ❌
이유: 해커톤 시연에서 위험함
```

**방법 C: Hybrid (Detection + Fallback)**
```
1순위: Anomaly Detection 밴드 사용
2순위: 없으면 Fallback 임계값 사용

장점: 안정적이면서 지능적
단점: 구현 복잡
결정: ✅ 선택!
이유:
  - 항상 작동 보장 (시연 안전)
  - ML 장점 활용
  - 실용성 확보
```

### 질문 3: 상태를 몇 단계로?

#### 검토한 옵션

**2단계 (정상/위험)**
```
결정: ❌
이유: 너무 단순, 중간 상태 표현 불가
```

**5단계 (매우좋음/좋음/보통/나쁨/매우나쁨)**
```
결정: ❌
이유:
  - 너무 복잡
  - 펭귄 표정 5개 필요 (리소스 과다)
  - 해커톤 기간 내 제작 불가능
```

**3단계 (건강/주의/위험)**
```
건강: 0~30점 (초록, 웃는 펭귄)
주의: 31~70점 (노랑, 보통 펭귄)
위험: 71~100점 (빨강, 우는 펭귄)

결정: ✅ 선택!
이유:
  - 신호등 비유 (직관적)
  - 3개 표정 제작 가능
  - 명확한 구분
```

## 🔧 기술 결정 회의 (자체)

### 결정 1: Python vs Java?

**상황**:
- 승규님은 Python 더 익숙
- Backend 팀은 Java (Spring Boot)

**옵션 비교**:
```
A. Java 직접 구현
  시간: 2일
  위험: 높음 (익숙하지 않음)

B. Python만 구현
  시간: 0.5일
  위험: 통합 어려움

C. Python → Java 이식
  시간: 1일 (Python) + 1일 (이식 지원)
  위험: 낮음
```

**결정**: C 선택
```
이유:
1. 빠른 프로토타이핑 (Python)
2. 테스트 용이
3. Java 팀에게 "명세서" 제공
4. 승규님 강점 활용
```

---

### 결정 2: 메트릭 가중치

**논의**: 어떤 메트릭이 가장 중요한가?

**분석**:
```
에러율:
  - 사용자에게 직접 영향
  - 가장 심각한 지표
  - 가중치: 50%

레이턴시:
  - 사용자 경험 직결
  - 이탈률에 영향
  - 가중치: 35%

CPU:
  - 간접 지표
  - 잠재적 위험
  - 가중치: 15%
```

**결정**: 50% / 35% / 15%
```
근거:
- 실제 장애 사례 분석
- 사용자 영향도 기준
- 심사위원 납득 가능한 논리
```

### 결정 3: Fallback 임계값

**참고 자료**:
- AWS Best Practices
- Google Performance 가이드
- 일반적인 SLA

**최종 값**:
```
에러율:
  정상 <1%, 주의 1~5%, 위험 >5%
  근거: AWS 권장 에러율 1% 이하

레이턴시:
  정상 <300ms, 주의 300~700ms, 위험 >700ms
  근거: Google 연구 - 300ms 이상 시 이탈 증가

CPU:
  정상 <50%, 주의 50~80%, 위험 >80%
  근거: 일반적 임계값 + 버퍼 확보
```

**검증 방법**:
```
1. Python으로 시뮬레이션
2. 다양한 값으로 테스트
3. 결과가 직관과 일치하는지 확인
```

## 💡 핵심 인사이트

### 1. "완벽한 기술" < "작동하는 기술"
```
Anomaly Detection만: 완벽하지만 불안정
Hybrid 방식: 완벽하진 않지만 안정적

선택: Hybrid
이유: 해커톤은 "작동"이 최우선
```

### 2. "복잡한 설명" < "직관적 경험"
```
복잡한 알고리즘: 이해 어려움
0~100점 + 펭귄: 즉시 이해

선택: 단순화
이유: 사용자 경험이 기술보다 중요
```

### 3. "혼자 잘하기" < "팀 같이 잘하기"
```
완벽한 코드: 나만 이해
문서 + 가이드: 팀 전체 이해

선택: 문서화
이유: 해커톤은 팀워크가 생명
```
