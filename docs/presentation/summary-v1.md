#### 받은 요구사항
- CloudWatch 메트릭(에러율, 레이턴시)에 Anomaly Detection 적용
- 배포가 "즐겁고 기분 좋은 경험"이 되도록 만들기
- 팀원들과 협업 가능한 명확한 설계 필요

#### 첫 번째 고민: 어떻게 "즐거운 배포"를 만들까?

**검토한 방안들**:

1. **방안 A: 단순 알람 시스템**
   - CloudWatch Alarm만 설정
   - 이메일/SMS로 알림
   - ❌ 기존 시스템과 차별점 없음
   - ❌ "즐겁다"는 느낌 전혀 없음

2. **방안 B: 대시보드 + 그래프**
   - Grafana 같은 모니터링 대시보드
   - 실시간 그래프 표시
   - ⚠️ 초보자가 이해하기 어려움
   - ⚠️ "즐겁다"보다는 "복잡하다"

3. **방안 C: 점수 + 게이미피케이션** ✅ 선택!
   - 0~100점으로 단순화
   - 펭귄 캐릭터가 코칭
   - 상태에 따라 애니메이션 변화
   - ✅ 직관적이고 이해하기 쉬움
   - ✅ "재미" 요소 자연스럽게 추가 가능
   - ✅ 초보자도 즉시 이해

**선택 이유**:
- 해커톤 주제: "배포가 즐거운 경험"
- 게임처럼 점수를 보면 즉시 이해 가능
- 펭귄이라는 캐릭터로 감정적 연결
- 기술적으로도 Anomaly Detection을 활용하면서 UX 극대화

### 10:00 - 점수 계산 방식 설계

#### 고민: 어떻게 점수를 계산할까?

**검토한 방안들**:

1. **방안 A: 단순 임계값**
   ```
   에러율 > 5% → 100점
   에러율 < 1% → 0점
   ```
   - ❌ 너무 단순함
   - ❌ Anomaly Detection을 활용하지 못함
   - ❌ "평소와 다르다"를 감지 못함

2. **방안 B: Anomaly Detection만 사용**
   ```
   밴드 벗어남 → 100점
   밴드 안 → 0점
   ```
   - ⚠️ 초기 데이터 부족 시 작동 안 함
   - ⚠️ 해커톤 시연에서 문제 발생 가능
   - ❌ 위험 부담 큼

3. **방안 C: Hybrid (Anomaly Detection + Fallback)** ✅ 선택!
   ```
   1. Anomaly Detection 밴드 있으면 우선 사용
   2. 없으면 하드코딩된 임계값으로 대체
   3. 벗어난 정도에 따라 점수 계산
   ```
   - ✅ 안정성: 항상 작동함
   - ✅ 지능성: ML 활용
   - ✅ 시연 안전: Fallback으로 보장

**선택 이유**:
- 해커톤 특성상 실제 데이터가 부족할 수 있음
- 시연 중 "데이터 없어서 안 됩니다"는 최악의 시나리오
- Anomaly Detection의 장점은 살리면서 안정성 확보

### 11:00 - 메트릭 가중치 결정

#### 고민: 어떤 메트릭이 가장 중요한가?

**검토한 방안들**:

1. **방안 A: 동등 가중치**
   ```
   에러율 33% + 레이턴시 33% + CPU 33%
   ```
   - ⚠️ 실제로 에러율이 가장 심각한데 무시됨
   - ❌ 현실 반영 부족

2. **방안 B: 에러율 100%**
   ```
   에러율 100%
   ```
   - ❌ 다른 메트릭 무시
   - ❌ 레이턴시나 CPU 과부하 감지 못함

3. **방안 C: 차등 가중치** ✅ 선택!
   ```
   에러율 50% + 레이턴시 35% + CPU 15%
   ```
   - ✅ 에러율이 가장 중요 (사용자에게 직접 영향)
   - ✅ 레이턴시도 중요 (사용자 경험)
   - ✅ CPU는 간접 지표 (낮은 가중치)

**선택 이유**:
- 실제 장애 사례 분석:
  - 에러율 급증 → 즉시 사용자 영향
  - 레이턴시 증가 → 사용자 이탈
  - CPU 높음 → 잠재적 위험
- 심사위원이 납득할 수 있는 논리적 근거

### 12:00 - 상태 분류 기준 설정

#### 고민: 몇 단계로 나눌까?

**검토한 방안들**:

1. **방안 A: 2단계 (정상/위험)**
   - ❌ 너무 단순함
   - ❌ "조금 주의" 같은 중간 상태 표현 불가

2. **방안 B: 5단계 (매우좋음/좋음/보통/나쁨/매우나쁨)**
   - ❌ 너무 복잡함
   - ❌ 펭귄 표정도 5개 필요 (리소스 과다)

3. **방안 C: 3단계 (건강/주의/위험)** ✅ 선택!
   ```
   0~30점: 건강 (초록, 웃는 펭귄)
   31~70점: 주의 (노랑, 보통 펭귄)
   71~100점: 위험 (빨강, 우는 펭귄)
   ```
   - ✅ 신호등 시스템 (직관적)
   - ✅ 3개 표정만 필요 (구현 가능)
   - ✅ 명확한 구분

**선택 이유**:
- 신호등 비유: 누구나 이해
- 펭귄 표정 3개는 해커톤 기간 내 제작 가능
- 지나치게 세분화하면 오히려 혼란

### 15:00 - Fallback 임계값 설정

#### 고민: 임계값을 어떻게 정할까?

**참고한 자료들**:
- AWS Best Practices
- 실제 운영 경험 (추정)
- 일반적인 서비스 수준

**최종 결정**:

| 메트릭 | 정상 | 주의 | 위험 | 근거 |
|--------|------|------|------|------|
| 에러율 | <1% | 1~5% | >5% | AWS 권장: 에러율 1% 이하 |
| 레이턴시 | <300ms | 300~700ms | >700ms | Google: 300ms 이상 시 이탈률 증가 |
| CPU | <50% | 50~80% | >80% | 일반적 임계값: 80% 이상 위험 |

**왜 이 값들인가?**:
- 에러율 1%: AWS 모범 사례
- 레이턴시 300ms: 사용자 체감 시작점
- CPU 50%: 버퍼 확보 (급격한 증가 대비)

### 3. "혼자"보다 "팀"

- 맞춤 설명 → 효율적 커뮤니케이션
